# v0.10 Ghost Publication Doctor

Status: detailed implementation plan; implementation has not started.

## Product decision

Ghost Publisher should add a diagnostic workflow, not broaden into Ghost administration.

The v0.10 release will add:

1. One read-only `check_site_health` tool for bounded, server-selected public checks.
2. Backward-compatible `audit_content` findings for accessibility, card integrity, links, metadata, and media readiness.
3. One user-invoked `ghost_publication_doctor` prompt that composes existing reads, the two diagnostic tools, and the existing signed preview/apply path.
4. Deterministic Ghost 5 and Ghost 6 fixtures for every finding and live check.

It will not add arbitrary URLs, crawling, JavaScript execution, theme or route mutation, general API dispatch, deletion, members, newsletters, analytics administration, persistent storage, or an embedded AI provider.

## Assumptions

- v0.9.0 native authoring is published before v0.10.0 is tagged.
- The current local stdio, one-configured-site model remains the release target.
- `check_site_health` is available in every permission profile because it is read-only.
- Ghost-returned public URLs and configured public URL templates remain the only content URL authorities.
- A host browser may perform a separately requested interaction check, but the MCP server will not execute page JavaScript or simulate clicks.
- Existing `updated_at`, preview hash, exact scopes, revision saving, readback, and literal confirmation controls remain unchanged.
- No completion dates are assigned until maintainer capacity is known.

## Research basis

The plan responds to concrete Ghost failure modes without claiming to repair Ghost core:

| Ghost issue | Observable failure | v0.10 response | Explicit limit |
| --- | --- | --- | --- |
| [#27415](https://github.com/TryGhost/Ghost/issues/27415) | Share UI can be present while the required Portal script is absent | Detect share markup plus missing Portal prerequisite on exact sampled posts | Does not click the share control or change Ghost settings |
| [#29991](https://github.com/TryGhost/Ghost/issues/29991) | Ghost 6 can generate extension-bearing collection URLs that return 404 | Report an extension-bearing generated URL returning 404 with Ghost version evidence | Does not edit `routes.yaml`, redirects, middleware, or themes |
| [#27462](https://github.com/TryGhost/Ghost/issues/27462) | Toggle cards have screen-reader problems | Flag toggle cards as a manual accessibility review requirement | Does not silently replace or rewrite toggle cards |
| [#29221](https://github.com/TryGhost/Ghost/issues/29221) | Copied galleries can share mutation behavior | Report identical gallery payload fingerprints as a heuristic review finding | Does not claim duplication proves corruption and does not rewrite galleries |
| [#24640](https://github.com/TryGhost/Ghost/issues/24640) | Unsplash search can return results for a partial query | Continue recommending host image generation/search plus existing safe upload | Adds no Unsplash client or image-provider key |
| [#24600](https://github.com/TryGhost/Ghost/issues/24600) | Social image generation can omit remote avatar/cover assets | Check Ghost-returned image reachability and response metadata on exact samples | Does not reproduce Ghost's social-image renderer |
| [#29220](https://github.com/TryGhost/Ghost/issues/29220) | Complex-script IME input can fail at the beginning of editor blocks | Document that native MCP draft creation bypasses initial typing, while retaining manual review | Adds no automatic language rewriting |
| [#23441](https://github.com/TryGhost/Ghost/issues/23441) | Date filtering can produce incorrect same-day results in a Ghost/SQLite path | Keep MCP pagination and timestamp comparisons exact; park cross-check reporting for v0.11 | Does not patch Ghost's theme or database filtering |

The design also adopts three non-Ghost MCP lessons:

- Follow the [GitHub MCP server](https://github.com/github/github-mcp-server/blob/main/docs/server-configuration.md) pattern of capability restriction: read-only mode must remove or technically block writes.
- Follow the [Sentry MCP](https://github.com/getsentry/sentry-mcp) pattern of workflow-focused diagnosis rather than mirroring an entire upstream API.
- Follow the [Notion MCP](https://developers.notion.com/guides/mcp/mcp-supported-tools) pattern of composing small tools, without inventing a persistent Ghost review-comment API that Ghost does not expose as a stable integration surface.

## Target user journey

### Draft readiness

1. The user asks to review named drafts or Pages.
2. The host resolves exact targets using `list_posts`, `list_pages`, `get_post`, or `get_page`.
3. `audit_content` returns deterministic findings with evidence and certainty.
4. The prompt separates automatically fixable metadata/text findings from manual card or theme review.
5. If a safe draft-only remediation exists, the host calls `preview_changes` and shows the exact patch, snapshot, scopes, and hash.
6. The workflow stops for explicit approval.
7. After approval, `apply_change_set` runs once and `audit_content` verifies the result.
8. The workflow does not publish.

### Published-site diagnosis

1. The user invokes `ghost_publication_doctor` for the configured site and, optionally, up to five exact published post/Page targets.
2. `check_connection` reports the Ghost version and configured public surfaces.
3. `check_site_health` checks only server-derived URLs.
4. `audit_content` checks the exact Ghost records.
5. The prompt reports confirmed failures, heuristic warnings, and unavailable evidence separately.
6. Published bodies are never changed. Any metadata proposal is handed to the existing SEO workflow and requires its separate approval.

### Upgrade rehearsal

The full before/after comparison is a v0.11 workflow, but v0.10 must return stable, serializable evidence that a client can save manually:

- Ghost version.
- Site and target identifiers.
- Checked public URL without credentials.
- HTTP status and content type.
- Canonical and title markers.
- Finding codes, certainty, and evidence.
- Check timestamp.

No snapshot database or background monitor is introduced.

## v0.10 tool contract

### `check_site_health`

Purpose: perform a bounded set of public checks using only site and content URLs selected by the server.

Proposed input:

```json
{
  "posts": [
    {
      "id": "24-character Ghost ID",
      "updated_at": "exact Ghost timestamp"
    }
  ],
  "pages": [
    {
      "id": "24-character Ghost ID",
      "updated_at": "exact Ghost timestamp"
    }
  ]
}
```

Input rules:

- Both arrays are optional, but their combined size is at most five.
- Duplicate content targets are rejected.
- Caller-provided URLs, hosts, paths, ports, headers, cookies, methods, and redirect policies are not accepted.
- Exact `updated_at` is required so the report is bound to a known Ghost revision.
- The tool performs no write and is registered in all permission profiles.

Server-selected checks:

1. Read `/site/` for title, public URL, and Ghost version.
2. Validate the returned public base with the existing public-URL and DNS protections.
3. GET the public homepage once.
4. GET `/sitemap.xml` once from the validated public base.
5. Read each exact target from Ghost and reject stale revisions.
6. Select each target URL from its configured template or Ghost-returned URL using the same precedence as existing live checks.
7. GET each selected target once.
8. Optionally GET each target's Ghost-returned feature image once, capped by the combined target limit.
9. Never fetch links discovered inside arbitrary post content.

Proposed output shape:

```json
{
  "site": {
    "title": "Publication title",
    "url": "https://publication.example/",
    "ghost_version": "6.x",
    "checked_at": "ISO-8601 timestamp"
  },
  "checks": [
    {
      "code": "SITE_HOMEPAGE_HTTP",
      "result": "pass",
      "certainty": "confirmed",
      "target": "site",
      "url": "https://publication.example/",
      "evidence": {
        "status": 200,
        "content_type": "text/html"
      },
      "message": "Homepage returned HTTP 200.",
      "ghost_issue": null,
      "suggested_action": null
    }
  ],
  "summary": {
    "pass": 1,
    "warning": 0,
    "fail": 0,
    "unavailable": 0
  }
}
```

Output rules:

- `result` is `pass`, `warning`, `fail`, or `unavailable`; no quality score is returned.
- `certainty` is `confirmed` or `heuristic`.
- Evidence is mechanical and bounded; model-authored conclusions do not come from the tool.
- A failed diagnostic result is returned as structured data, not as an MCP protocol error.
- Invalid input, blocked URLs, authentication failure, stale revision, or an internal invariant failure is an MCP error.
- Secret-bearing URLs, response bodies, headers, cookies, Admin keys, and deployment-hook paths are never returned.

## `audit_content` extension

The existing fields remain unchanged for backward compatibility. Add a `findings` array to each audit result.

Proposed finding shape:

```json
{
  "code": "CARD_TOGGLE_A11Y_REVIEW",
  "severity": "warning",
  "certainty": "confirmed",
  "message": "The draft contains a toggle card that requires manual screen-reader review.",
  "evidence": {
    "node_type": "toggle",
    "node_indexes": [4]
  },
  "ghost_issue": "https://github.com/TryGhost/Ghost/issues/27462",
  "safe_fix": {
    "available": false,
    "reason": "No proven structure-preserving toggle conversion exists."
  }
}
```

Finding requirements:

- Finding codes are stable machine identifiers.
- Messages are deterministic and do not claim truth, quality, legal compliance, accessibility certification, or ranking impact.
- Evidence contains node types, indexes, field names, statuses, or URLs—not full secret-bearing payloads.
- `safe_fix.available` means an existing bounded change operation can represent the fix without losing structure.
- The tool never creates a change set itself.
- Heuristics must say `certainty: heuristic` and may not be described as confirmed defects.

## Static HTML diagnostic rules

The server may parse HTML but must not execute it.

### Share prerequisites

Report `SHARE_PORTAL_PREREQUISITE_MISSING` only when both are mechanically observed:

1. The sampled target contains a known Ghost share trigger marker or a `#/share` link.
2. No Portal script marker is present in the same response.

Always add `SHARE_INTERACTION_UNVERIFIED` because static HTML does not prove that a popup opens, focuses correctly, or works after hydration.

### Extension-bearing routes

Report `ROUTE_EXTENSION_404_GHOST6` only when all are true:

1. Ghost reports major version 6.
2. The exact Ghost- or template-selected content URL path contains a file extension.
3. That exact URL returns HTTP 404.

Do not infer a `routes.yaml` configuration, propose an automatic rewrite, or report the Ghost issue as the confirmed root cause when the version or URL evidence is unavailable.

### Gallery duplication heuristic

Normalize each gallery to its ordered image identity fields and relevant card settings, hash the normalized value, and report equal hashes only when two separate gallery nodes match. The finding must remain heuristic because intentionally repeated galleries are valid and the open Ghost bug concerns later editor mutation behavior.

## Network and security contract

`check_site_health` must retain or tighten every existing live-check boundary:

- GET only; no caller-selected method.
- No cookies, Ghost Admin authentication headers, custom headers, or browser session state.
- HTTPS only except explicit localhost development.
- Reject embedded credentials.
- Reject private, loopback, link-local, multicast, and otherwise non-public resolved addresses, except configured localhost development.
- Validate every server-derived URL again immediately before the request.
- Do not follow redirects in v0.10; return redirect status as evidence without revealing a sensitive `Location` value.
- Fifteen-second timeout per request.
- Two-megabyte response limit.
- Maximum five exact content targets.
- Maximum twelve requests in one tool call, including homepage, sitemap, targets, and feature images.
- Maximum four concurrent public requests.
- No automatic retry.
- Never fetch URLs found inside body links, scripts, CSS, sitemaps, embeds, or bookmarks.
- Never log or return response bodies, Admin keys, deploy-hook URLs, cookies, authorization data, or filesystem paths.

## `ghost_publication_doctor` prompt contract

The prompt is user-invoked and available in all permission profiles because its diagnostic path is read-only. A read-only profile must stop before remediation.

Required workflow:

1. Call `check_connection` and report the exact site, Ghost version, and configured public-check surfaces.
2. Resolve only the user-named posts or Pages. If none are named, ask for a bounded target set rather than auditing an entire publication.
3. Call `audit_content` for at most 25 exact targets.
4. Call `check_site_health` for at most five exact published targets.
5. Separate results into confirmed failures, heuristic review items, unavailable evidence, and passes.
6. State which results correspond to open Ghost issues and which are publication-specific.
7. Never say the MCP fixed Ghost core.
8. For a draft-safe finding, prepare the smallest existing change operation and call `preview_changes`.
9. Show the exact target, snapshot, proposed operation, affected fields/nodes, scopes, warnings, and preview hash.
10. Stop for explicit approval.
11. In a writable profile, call `apply_change_set` once only after approval and only for draft targets in this workflow.
12. Re-run the relevant read-only audit/check without repeating a write.
13. For published content, return a proposal or direct the user to `ghost_seo_optimize`; do not change the published body.
14. Never publish, unpublish, schedule, deploy, create a webhook, or invoke a newsletter operation.

## Release gates

### Functional

- Every documented code is emitted by a deterministic fixture.
- Confirmed and heuristic results cannot be confused in the schema.
- Existing `audit_content`, live-check, preview, apply, and permission-profile contracts remain compatible.
- Diagnostics never mutate Ghost or public infrastructure.

### Safety

- No arbitrary URL or crawler surface exists.
- DNS and public-address protections cover every new request.
- No response body, secret, private host, filesystem path, or authenticated header leaks.
- Diagnostic prompts cannot bypass exact approval or write scopes.

### Compatibility

- Unit, lint, typecheck, build, and package smoke pass on supported Node versions.
- Disposable Ghost 5 and Ghost 6 workflows pass.
- MCP initialization, tool listing, calls, structured output, and prompt discovery pass.

### Documentation

- README tool table and safety model match the released schema.
- Changelog and roadmap distinguish shipped behavior from later work.
- Issue references are current at release time and described as evidence, not guarantees.
- Support examples contain no real site secret or private URL.

## Metrics without telemetry

The MCP will not add analytics or phone-home telemetry. Adoption and usefulness can be assessed through opt-in evidence:

- GitHub compatibility reports.
- Redacted support bundles voluntarily attached to issues.
- Maintainer-run fixture counts and release workflow results.
- Explicit pilot feedback describing which finding led to a useful action.

Do not claim reduced incidents, accessibility compliance, SEO gains, or time savings without real measured evidence.

## Risks and mitigations

| Risk | Consequence | Mitigation |
| --- | --- | --- |
| Static HTML produces false confidence about interactive sharing | A page appears healthy while the click path fails | Always return `SHARE_INTERACTION_UNVERIFIED`; recommend a host-browser check |
| Ghost changes markup across versions/themes | Brittle selector-based findings | Use multiple bounded markers, versioned fixtures, and `unavailable` rather than guessing |
| Duplicate galleries are intentional | False defect report | Mark fingerprint result heuristic and require manual review |
| Public site URL points to private infrastructure | SSRF or internal data access | Reuse URL/DNS checks and reject private addresses except explicit localhost tests |
| Headless and Ghost-rendered sites differ | Incorrect assumptions about sitemap, Portal, or canonical ownership | Label surfaces and checks separately; do not transfer findings between origins |
| Tool output becomes a pseudo-quality score | Users over-trust mechanical results | Return categorical evidence only; prohibit aggregate quality scoring |
| Prompt implies approval | Unintended writes | Invocation is never approval; signed preview and literal confirmation remain mandatory |
| Issue-specific workarounds become stale | Misleading advice after Ghost fixes an issue | Re-check referenced issue state and Ghost fixtures before each release |

## v0.11 follow-up: upgrade and support workflows

Do not pull these into v0.10 unless the v0.10 pilot proves the diagnostic evidence is stable.

### Upgrade rehearsal

- Define a portable baseline document from `check_site_health` output.
- Compare before/after Ghost versions without a server database.
- Report added, resolved, and unchanged findings.
- Bind comparisons to exact site and target identifiers.
- Never perform the Ghost upgrade or edit routes/themes.

### Redacted support bundle

- Produce copy-ready Markdown from deterministic tool output.
- Include environment, reproduction, expected/observed behavior, finding codes, and safe evidence.
- Exclude keys, cookies, private addresses, full bodies, filesystem paths, and unrelated content.
- Require user review before opening a Ghost or project issue.

### Date-order cross-check

- Read a bounded exact page of posts.
- Compare API order against normalized timestamps.
- Report duplicates, gaps, and inconsistent ordering without inventing missing records.
- Do not add arbitrary NQL or a local content database.

## Later: composition, not expansion

### Media workflow

Keep host image generation/search outside the MCP. The server should validate, upload, and verify Ghost assets through the existing safe flow. Add no second image-provider key.

### Analytics and performance insight

Compose Search Console, OpenSEO, or a dedicated analytics MCP with Ghost Publisher. Do not proxy internal Tinybird calls or duplicate Ghost Stats administration. Any future adapter must be read-only, bounded, cached, and based on a stable documented API.

### Persistent editorial review

Use the host, GitHub, Notion, or another explicit review system when persistent comments are required. Do not invent Ghost comments, hidden tags, draft metadata, or a database solely to imitate Notion.

## Out of scope / parking lot

- Arbitrary site crawling or caller-supplied URLs.
- Browser automation inside the MCP server.
- Theme upload, activation, source editing, or validation as a write.
- `routes.yaml` or redirects upload/edit.
- Ghost upgrade execution.
- Database migration or collation changes.
- Members, tiers, offers, newsletters, newsletter sending, Portal preferences, or transactional email configuration.
- Webhook creation, update, deletion, or inspection.
- Analytics administration or Tinybird proxying.
- Deletion of posts, Pages, media, tags, members, or any other resource.
- Arbitrary Ghost Admin API calls or NQL.
- Automatic toggle/gallery rewriting.
- AI translation of Ghost product localization files; Ghost's i18n issue explicitly requires fluent human translation review.
- Embedded LLM, image-provider billing, background agents, databases, dashboards, telemetry, or persistent approval state.
